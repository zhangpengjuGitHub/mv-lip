# Kaggle 部署 MuseTalk 1.5 踩坑清单

2026-11-03 在 Kaggle T4 新会话（Python 3.13 / torch 2.11+cu128 / CUDA 12.8，磁盘 28G）实测，
按踩到的顺序排列。全部已固化进 `kaggle/setup_musetalk.sh` 与 `kaggle/run_lipsync.py`，脚本幂等可重跑。

## 0. 为什么不能用系统 Python

Kaggle 默认 **Python 3.13 + torch 2.11 + CUDA 12.8**，而 MuseTalk 官方要求
**Python 3.10 + torch 2.0.1 + cu118**。MMLab 全家桶（mmcv/mmdet/mmpose）在 3.13 上没有 wheel。
解法：`uv venv --python 3.10 /kaggle/working/mtenv` 建独立环境（Kaggle 自带 `uv`，没有 conda）。

## 1. venv 已存在时 `uv venv` 直接报错退出

```
A virtual environment already exists at: mtenv
hint: Use the '--clear' flag or set 'UV_VENV_CLEAR=1'
```
`set -e` 会让整个脚本挂掉。改成 `if [ ! -x .../bin/python ]; then uv venv ...; fi`。

## 2. `mim` 报 `No module named 'pkg_resources'`

uv 创建的 venv 默认**不带 setuptools**，而 openmim 依赖 `pkg_resources`。
解法：`uv pip install "setuptools<81" wheel`。

## 3. `chumpy` 构建 wheel 失败

mmpose 的老依赖 chumpy 走 PEP 517 隔离构建时，隔离环境里没有 numpy，报
`Getting requirements to build wheel did not run successfully`。
解法：`uv pip install chumpy --no-build-isolation`（用当前环境的 numpy + setuptools），
装好后 `mim install mmpose` 会跳过它。

## 4. `numpy.core.multiarray failed to import`

uv 解析时把 numpy 升到了 2.x，而 mmcv / opencv 的 wheel 是按 numpy 1.x ABI 编译的。
解法：显式 `uv pip install "numpy==1.26.4"`。

## 5. `ModuleNotFoundError: No module named 'toml'`（来自 yapf / mmengine）

Python 3.10 没有内置 `tomllib`，mmengine 的 `config.py` 经 yapf 会 fallback 到 `toml`。
解法：`uv pip install toml "yapf==0.40.2"`。

## 6. 官方 `download_weights.sh` 在 Kaggle 下不全

官方脚本用 `HF_ENDPOINT=https://hf-mirror.com`（国内镜像）+ `gdown`（Google Drive），
实测**只下到 2 个文件 / 96M**。改用 `kaggle/dl_weights.py`，走官方 huggingface.co
逐个仓库下载，实测 **9.28 GB / 49 个文件**齐全。
`face-parse-bisent/79999_iter.pth` 走 gdown 兜底，`resnet18` 从 download.pytorch.org 拉。

## 7. 推理时 `ValueError: Key backend: 'module://matplotlib_inline.backend_inline'`

Kaggle/Jupyter 会往环境变量注入 `MPLBACKEND=module://matplotlib_inline.backend_inline`，
MuseTalk 依赖的老版 matplotlib 不认这个值，import 阶段直接崩。
解法：`run_lipsync.py` 启动子进程时强制 `env["MPLBACKEND"] = "Agg"`。

## 9. 全片 1080p 推理吃满 30GB 内存（2026-11-04，最贵的一课）

`scripts/inference.py` 的 `read_imgs()` 会把**整段视频所有帧一次性读进内存**：
194s × 25fps = 4853 帧 × 1920×1080×3B ≈ **28.8 GiB**，再加 `res_frame_list`、
latent、模型，峰值实测 **30.8 GB**，正好顶死 Kaggle 容器。后果链：

- 日志里有**两个进度条**：`/4853` 是逐帧人脸检测（39 分钟），`/607` 才是 UNet 生成。
  把前者看到 100% 当成"快出片了"是误判，真实进度当时只有 22%。
- 内存顶死后 swap 抖动，速率从 1.84 s/it 劣化到 **133~162 s/it**（30 秒才推进 1 批）。
- 最终 Kaggle 弹 `Your notebook tried to allocate more memory than is available.
  It has restarted.`，kernel 重启并把推理进程一起杀掉。

解法固化为 `kaggle/rescue_run.py`：

| 动作 | 原因 |
|---|---|
| 输入降到 1280×720 | 帧内存 28.8 → 12.8 GiB，总峰值约 15 GB |
| 复用 `results/mv_clean_25fps.pkl` 并把每个 bbox ×2/3 | 人脸检测 39 分钟已跑完，不必重做 |
| 缩放后的视频**必须保持同名** `mv_clean_25fps.mp4`（换目录即可） | pkl 文件名取自输入视频 basename，改名就命中不了 |
| 清空 `results/mv_lip/v15/` | 否则会拿 1080p 旧帧配 720p 坐标 |
| 加 `--use_saved_coord --saved_coord` | 前者读坐标，后者防止跑完把 pkl 删掉 |
| `start_new_session=True` 脱离 kernel | kernel 被 OOM 重启也杀不掉推理 |

## 10. 无人值守：三层保活 + 自动回传

- **Kaggle 侧** `rescue_run.py`：脱离进程；每 60s 检查一次，每 5 分钟推
  `rescue_status.json` 到私有仓库；成片后按 20MB 分块 + sha256 manifest 回传 `final_lip`。
- **kernel 侧**：console 里跑一个前台心跳（每 240s 打印一行 `HB`），
  让 websocket 持续有流量，避免 idle 判定。纯输出，不碰 notebook 内容。
- **本机侧** `kaggle/watchdog_local.py`：每 5 分钟把 Chrome 置前并微移鼠标
  （不点击、不按键，不会误触页面），同时轮询 manifest；一旦出现就自动
  下载 → 校验 → 叠回 `song_final.mp3` → lanczos 放大 1080p → 生成 44/94/119/150/158s
  质检拼图 → 回传 `final_mv` 与 `DONE.txt`。
- **兜底**：即使本机守护挂掉，Kaggle 侧也已把 `final_lip` 推到 GitHub，素材不会丢。
